# CSV, JSON and SQL import engines

Imports are available from an editable table’s **Import data** action. Choose CSV, JSON object array or Klyndb JSON export, select a native file, review the preview and field mapping, then append rows. Changing the format or parsing options requires updating the preview. Production connections require explicit review confirmation. SQL files run from the connected editor’s **Import SQL** action or the command palette; they do not use table field mapping.

`klyndb-import` copies an explicitly selected regular file into a private temporary snapshot. Preview and execution read those same bytes, even if the original file changes. The source is read incrementally; file contents are not transferred to React. Snapshot size is limited to 512 MiB, decoded CSV records and encoded JSON records to 8 MiB, and records to 1,000 fields. The desktop registry retains at most four snapshots and 512 MiB in aggregate. IPC exposes opaque source/job IDs and a basename, never arbitrary frontend file paths. Each source starts at most one job; choose the file again to retry.

CSV requires UTF-8 and a header row. An optional UTF-8 BOM, CRLF, embedded quoted newlines and doubled quotes are supported. Malformed quotation, inconsistent field counts and invalid UTF-8 fail explicitly. Comma, semicolon, tab and pipe separators are supported. The preview contains up to five rows with clipped values. Headers are limited to 256 bytes each and 64 KiB total.

JSON object import accepts a UTF-8 array of objects, optionally with a BOM:

```json
[
  {"id": 1, "name": "Ada", "note": null, "payload": {"active": true}},
  {"payload": {"active": false}, "note": "", "name": "Lin", "id": 2}
]
```

The first object supplies the field names; subsequent objects may reorder those keys but must contain exactly the same set. Missing/extra fields, duplicate keys at any depth, invalid UTF-8, malformed syntax, a trailing comma or trailing data fail the import. An empty array has no importable fields. JSON object keys are limited to 1,000 at each depth and nesting is bounded to 128 levels. Records are framed and validated individually within the 8 MiB limit; the whole array is never materialized. JSONL is not an import format yet.

JSON `null` becomes database NULL. Empty strings, the string `"null"` and whitespace inside strings retain their meaning; CSV NULL/trim options do not apply. Number tokens remain exact strings in Rust, including large integers and precise decimals. Nested objects/arrays can map to JSON or serialized text. Choosing JSON for a scalar string stores a JSON string rather than parsing the string's contents as a document. Database storage types and coercion rules still apply, including the database's JSON numeric representation. The real MySQL contract demonstrates that its native JSON storage converts an integer larger than its integer range to a double; mapping that same value to a text column preserves every digit. Klyndb does not claim that database JSON storage preserves every input number.

Choose **JSON · Klyndb export** to import the app's typed JSON array export. Its explicit format avoids confusing ordinary objects named `columns` or `values` with export records. Every record must have matching `columns` and `values` arrays; the columns must remain identical and in the same order. Tagged NULL, number, boolean, text, binary and JSON cells are decoded in Rust. Duplicate source column names are preserved positionally; map them to distinct destination columns or ignore them. Destination value types remain an explicit mapping choice, so review them before starting.

Mapping is positional: each source field maps to one existing, non-generated destination column or is ignored. A destination can appear only once. Omitted destination columns use database defaults. Mapped values explicitly select text, number, boolean, hexadecimal binary or JSON. Numeric strings and JSON number tokens retain precision in Rust; the destination database still applies its own type and coercion rules. CSV whitespace trimming, an exact NULL token and empty-as-NULL are explicit choices; empty CSV fields otherwise remain empty text.

The producer sends bounded batches (up to 256 rows, normally 256 KiB) to the driver. A single larger row can use the existing 8 MiB mutation bound. A distinct completion message is sent only after successful EOF validation. A dropped producer never authorizes commit. The parsed-row counter is progress, not a count of committed rows.

SQLite, PostgreSQL, MySQL/MariaDB InnoDB, DuckDB and SQL Server source-build drivers hold their session lock for the entire stream, including waits for the parser. Another tab cannot commit between batches. DuckDB requires an idle session because its native engine has no savepoints: finish an active/failed transaction first. Refusal preserves caller-owned work. Supported scalar base tables accept CSV/standard JSON/typed JSON through the same mapping workflow; container/interval write types remain unsupported. On the other listed engines, an import owns a transaction when needed, or uses a savepoint inside the user's existing transaction. Success in a manual transaction remains pending for the user to commit or roll back. Ordinary parser/database errors roll back the import savepoint and preserve earlier caller-owned work. Native transaction aborts can invalidate that savepoint and undo the entire outer transaction: SQLite VM interruption is a verified example. Unconfirmed cleanup closes the session and reports a warning; verify data before retrying.

Read-only connections, generated columns and non-insert mutations are rejected. MySQL/MariaDB additionally reject non-InnoDB destination tables and conversion warnings. Nontransactional trigger effects can survive rollback; detected incomplete rollback closes the session and requires data verification before retrying. Database external effects are not guaranteed reversible.

Cancellation interrupts native work and parser waits. Final COMMIT/RELEASE is not deliberately interrupted after submission. PostgreSQL requires a synchronized cancellation response before session reuse; uncertain termination closes the connection. SQLite lock contention can still wait for its five-second busy timeout. The configured query timeout supplies a 1–3,600-second whole-file deadline. Progress counts parsed records; inserted rows appear only after native completion. Cancel waits for parser and database cleanup. Disconnect and native Quit cancel active imports and wait for completion; Escape cannot hide an active import dialog. A final commit already submitted may complete despite a late cancellation request.

The core job contract also checks production confirmation, immutable preview/execution, manual transactions, deadlines, disconnect/shutdown cleanup, single-use sources and registry limits on real SQLite/PostgreSQL/MySQL/MariaDB sessions. The frontend mapping check covers duplicate, generated and ambiguous names. `crates/core/tests/import.rs` exercises the real bounded CSV-to-driver flow. With disposable server URLs it covers SQLite, PostgreSQL and either MySQL or MariaDB: 1,201 quoted/multiline records, late parser failure, duplicate keys, producer loss, cancellation, manual transactions, concurrent COMMIT exclusion, read-only guards and incomplete nontransactional trigger rollback. `klyndb-import` also has a runnable parser/mapping/snapshot contract.

The JSON contract in `crates/core/tests/import.rs` exercises the actual source/job/parser/driver pipeline: 1,201 records, production confirmation, an immutable snapshot, NULL and quoted multiline text, exact numbers mapped to text, nested JSON, late syntax/key/schema/EOF failures with whole-import rollback, and a native JSON export roundtrip inside a manual transaction. It runs SQLite plus the explicitly configured PostgreSQL, MySQL and MariaDB fixtures. The parser contract checks bounds, nesting, fragmented/BOM input, exact JSON tokens, duplicate keys, cancellation and typed export records. The frontend check distinguishes real NULL from literal text and keeps CSV controls from changing JSON previews.

SQL Server CSV/JSON imports reuse its reviewed bound-value writer, including full destination-type casts, exact numeric/text/binary loss checks, generated-column protection and direct native counts. Disk-based base tables without enabled INSTEAD OF triggers are supported. One transaction/savepoint covers the entire file; ordinary late parser/constraint errors roll back earlier batches. Explicit and implicit transactions leave successful imports pending. The writer holds a table-wide exclusive lock until the transaction ends, and currently makes per-row native conversion/write requests; large-file throughput remains unmeasured. Core jobs use the configured whole-file deadline, with a separate one-hour driver ceiling. Cancellation drains native Attention before rollback/reuse; uncertain cleanup closes the session. See [SQL Server behavior and limits](SQLSERVER.md).

`crates/core/tests/mssql.rs` checks the real saved-session CSV/standard JSON/typed JSON pipeline: a captured immutable source, production review, generated-column refusal, 600 precise/quoted/multiline CSV rows, late malformed-record rollback, a typed native export roundtrip left pending inside a manual transaction, exact BIGINT/DECIMAL/binary/NULL values and a one-second slow-trigger timeout with whole-file rollback and same-session reuse. The real driver contract also verifies mandatory completion, producer loss, duplicate keys in a later batch, implicit transactions, reader-gap and active-trigger cancellation, concurrent-query exclusion and read-only refusal. Native SQL Server desktop import acceptance remains pending.

## SQL scripts

SQL file imports support SQLite, PostgreSQL and MySQL/MariaDB, plus DuckDB and SQL Server in source builds. DuckDB runs native original statements, drains SELECTs without display decoding and keeps script transactions under the user’s control. SQL Server runs native GO-separated batches, preserving variables across semicolons within a batch. Its preview/progress count completed batches.

Choose **Import SQL** on a connected SQL tab, select a UTF-8 file in the native picker, then review the statement count, clipped first five statements and destructive-query warnings. Rust copies the private snapshot and validates the entire file before enabling execution. A syntax error anywhere prevents the job from starting. Explicit review confirmation is required on every environment, with the production destination shown clearly.

The native drivers execute the original SQL in order while holding the connection for the whole stream, including waits for the reader. SELECT rows are drained and discarded rather than retained in React or in the result spool. Progress counts successfully completed statements, separately from statements read. A database error stops the script and reports the completed prefix; verify both earlier writes and the failing statement before retrying.

SQL scripts preserve their own transaction commands. They are **not automatically wrapped in an all-or-nothing transaction**. Earlier statements may already be committed, and MySQL/MariaDB DDL can implicitly commit even within BEGIN. An existing or script-created transaction can remain active or failed after completion/cancellation; the dialog and workbench show the actual state when available. Close the finished dialog and review COMMIT/ROLLBACK in the editor. Native cancellation and the configured 1–3,600-second timeout stop further execution; disconnect/shutdown wait for reader and driver cleanup. They do not promise to undo already committed SQL effects.

Files share the four-snapshot/512 MiB registry; each statement or SQL Server native batch is bounded to 4 MiB. Ordinary DDL, DML, queries and transaction statements accepted by the shared dialect parser are supported. The reader preserves strings, quoted identifiers, comments, PostgreSQL/DuckDB dollar strings and nested comments. UTF-8 BOM and a final statement without a semicolon are accepted. SQL INSERT exports use the source engine’s identifiers, string escapes and binary literals; exporting from a retained result remembers its original engine even after disconnect.

SQL Server accepts standalone case-insensitive GO lines, including inline comments; quoted/nested-comment GO text is preserved. SQL INSERT exports add GO boundaries. GO repeat counts, GO semicolons, SQLCMD commands/substitutions, MySQL DELIMITER, psql backslash commands, COPY STDIN/STDOUT dump streams and routine/trigger syntax outside the shared parser are unsupported. Other engines retain statement framing and reject compound bodies with unquoted internal semicolons. Unsupported syntax fails during preflight, before database execution. Executable MySQL/MariaDB comments remain rejected by the shared safety policy. SQL lexical-mode assignments are unsupported; native execution rechecks PostgreSQL standard_conforming_strings and MySQL/MariaDB ANSI_QUOTES/NO_BACKSLASH_ESCAPES before each statement, including after function calls that may change settings. Use standard_conforming_strings=on and disable those two MySQL modes for this import path. SQL Server checks native QUOTED_IDENTIFIER ON and rejects SHOWPLAN before every batch; explicit QUOTED_IDENTIFIER ON is allowed, while turning it off inside an imported file is refused. Native SQL Server batches can have effects even when the batch returns an error; inspect the failing batch as well as the completed prefix.

`crates/core/tests/sql_import.rs` runs the actual snapshot/job/driver pipeline on real SQLite/DuckDB files and configured PostgreSQL/MySQL/MariaDB/SQL Server fixtures. Its files exceed the editor limit, contain 1,201 precise/quoted/multiline/binary records and roundtrip through the native result spool’s SQL exporter. It verifies full-file preflight, immutable sources, confirmation/single-use guards, partial native failures, manual rollback, exclusion of concurrent COMMIT, producer loss, timeout cancellation and session reuse, and read-only refusal. DuckDB also verifies discarded nested types/large SELECTs, failed-transaction rollback and cancellation while waiting for the producer. The streaming reader has a fragmented-input, quoting, UTF-8, size and cancellation regression. Native desktop checks are recorded separately in the validation log.
