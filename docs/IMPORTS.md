# CSV and JSON import engine

Imports are available from an editable table’s **Import data** action. Choose CSV, JSON object array or Klyndb JSON export, select a native file, review the preview and field mapping, then append rows. Changing the format or parsing options requires updating the preview. Production connections require explicit review confirmation. SQL file imports remain on the roadmap.

`klyndb-import` copies an explicitly selected regular file into a private temporary snapshot. Preview and execution read those same bytes, even if the original file changes. The source is read incrementally; file contents are not transferred to React. Snapshot size is limited to 512 MiB, decoded CSV records and encoded JSON records to 8 MiB, and records to 1,000 fields. The desktop registry retains at most four snapshots and 512 MiB in aggregate. IPC exposes opaque source/job IDs and a basename, never arbitrary frontend file paths. Each source starts at most one job; choose the file again to retry.

CSV requires UTF-8 and a header row. An optional UTF-8 BOM, CRLF, embedded quoted newlines and doubled quotes are supported. Malformed quotation, inconsistent field counts and invalid UTF-8 fail explicitly. Comma, semicolon, tab and pipe separators are supported. The preview contains up to five rows with clipped values. Headers are limited to 256 bytes each and 64 KiB total.

JSON object import accepts a UTF-8 array of objects, optionally with a BOM:

```json
[
  {"id": 1, "name": "Ada", "note": null, "payload": {"active": true}},
  {"payload": {"active": false}, "note": "", "name": "Lin", "id": 2}
]
```

The first object supplies the field names; subsequent objects may reorder those keys but must contain exactly the same set. Missing/extra fields, duplicate keys at any depth, invalid UTF-8, malformed syntax, a trailing comma or trailing data fail the import. An empty array has no importable fields. JSON object keys are limited to 1,000 at each depth and nesting is bounded to 128 levels. Records are framed and validated individually within the 8 MiB limit; the whole array is never materialized. JSONL is not an import format yet.

JSON `null` becomes database NULL. Empty strings, the string `"null"` and whitespace inside strings retain their meaning; CSV NULL/trim options do not apply. Number tokens remain exact strings in Rust, including large integers and precise decimals. Nested objects/arrays can map to JSON or serialized text. Choosing JSON for a scalar string stores a JSON string rather than parsing the string's contents as a document. Database storage types and coercion rules still apply, including the database's JSON numeric representation. The real MySQL contract demonstrates that its native JSON storage converts an integer larger than its integer range to a double; mapping that same value to a text column preserves every digit. Klyndb does not claim that database JSON storage preserves every input number.

Choose **JSON · Klyndb export** to import the app's typed JSON array export. Its explicit format avoids confusing ordinary objects named `columns` or `values` with export records. Every record must have matching `columns` and `values` arrays; the columns must remain identical and in the same order. Tagged NULL, number, boolean, text, binary and JSON cells are decoded in Rust. Duplicate source column names are preserved positionally; map them to distinct destination columns or ignore them. Destination value types remain an explicit mapping choice, so review them before starting.

Mapping is positional: each source field maps to one existing, non-generated destination column or is ignored. A destination can appear only once. Omitted destination columns use database defaults. Mapped values explicitly select text, number, boolean, hexadecimal binary or JSON. Numeric strings and JSON number tokens retain precision in Rust; the destination database still applies its own type and coercion rules. CSV whitespace trimming, an exact NULL token and empty-as-NULL are explicit choices; empty CSV fields otherwise remain empty text.

The producer sends bounded batches (up to 256 rows, normally 256 KiB) to the driver. A single larger row can use the existing 8 MiB mutation bound. A distinct completion message is sent only after successful EOF validation. A dropped producer never authorizes commit. The parsed-row counter is progress, not a count of committed rows.

SQLite, PostgreSQL and MySQL/MariaDB InnoDB drivers hold their session lock for the entire stream, including waits for the parser. Another tab cannot commit between batches. An import owns a transaction when needed, or uses a savepoint inside the user's existing transaction. Success in a manual transaction remains pending for the user to commit or roll back. Ordinary parser/database errors roll back the import savepoint and preserve earlier caller-owned work. Native transaction aborts can invalidate that savepoint and undo the entire outer transaction: SQLite VM interruption is a verified example. Unconfirmed cleanup closes the session and reports a warning; verify data before retrying.

Read-only connections, generated columns and non-insert mutations are rejected. MySQL/MariaDB additionally reject non-InnoDB destination tables and conversion warnings. Nontransactional trigger effects can survive rollback; detected incomplete rollback closes the session and requires data verification before retrying. Database external effects are not guaranteed reversible.

Cancellation interrupts native work and parser waits. Final COMMIT/RELEASE is not deliberately interrupted after submission. PostgreSQL requires a synchronized cancellation response before session reuse; uncertain termination closes the connection. SQLite lock contention can still wait for its five-second busy timeout. The configured query timeout supplies a 1–3,600-second whole-file deadline. Progress counts parsed records; inserted rows appear only after native completion. Cancel waits for parser and database cleanup. Disconnect and native Quit cancel active imports and wait for completion; Escape cannot hide an active import dialog. A final commit already submitted may complete despite a late cancellation request.

The core job contract also checks production confirmation, immutable preview/execution, manual transactions, deadlines, disconnect/shutdown cleanup, single-use sources and registry limits on real SQLite/PostgreSQL/MySQL/MariaDB sessions. The frontend mapping check covers duplicate, generated and ambiguous names. `crates/core/tests/import.rs` exercises the real bounded CSV-to-driver flow. With disposable server URLs it covers SQLite, PostgreSQL and either MySQL or MariaDB: 1,201 quoted/multiline records, late parser failure, duplicate keys, producer loss, cancellation, manual transactions, concurrent COMMIT exclusion, read-only guards and incomplete nontransactional trigger rollback. `klyndb-import` also has a runnable parser/mapping/snapshot contract.

The JSON contract in `crates/core/tests/import.rs` exercises the actual source/job/parser/driver pipeline: 1,201 records, production confirmation, an immutable snapshot, NULL and quoted multiline text, exact numbers mapped to text, nested JSON, late syntax/key/schema/EOF failures with whole-import rollback, and a native JSON export roundtrip inside a manual transaction. It runs SQLite plus the explicitly configured PostgreSQL, MySQL and MariaDB fixtures. The parser contract checks bounds, nesting, fragmented/BOM input, exact JSON tokens, duplicate keys, cancellation and typed export records. The frontend check distinguishes real NULL from literal text and keeps CSV controls from changing JSON previews.
