ClickHouse connection workflow review: [official Beekeeper user documentation](https://docs.beekeeperstudio.io/user_guide/connecting/clickhouse/) on 2026-10-03. This covers selecting the engine, endpoint/database/credentials and TLS expectations; no implementation or commercial sources were read or reused. Klyndb independently uses a native TCP Rust client and shared connection/query/grid/export controls. Its schema view exposes the selected database, native column types and table DDL; unique relational keys, transactions and reviewed grid edits are not inferred from MergeTree sorting keys. Real native-protocol backend and verified-TLS contracts pass; native desktop acceptance remains pending.

ClickHouse plans independently use native `EXPLAIN PLAN json=1, indexes=1` through the existing bounded JSON tree/raw/export workflow, including read-only profiles. The fixed native prefix is normalized only for complete-query validation; original SQL is executed. Current driver runtime profiling and native desktop interaction remain pending. Reference: [official ClickHouse EXPLAIN documentation](https://clickhouse.com/docs/reference/statements/explain). No Beekeeper implementation or commercial source was reused.

SQL error navigation independently follows the [PostgreSQL protocol error fields](https://www.postgresql.org/docs/current/protocol-error-fields.html) and [SQLite error-offset API](https://www.sqlite.org/c3ref/errcode.html). Original PostgreSQL positions are mapped through the server encoding (including SQL_ASCII), while internal-query positions are omitted. SQLite batch suffix byte offsets and Unicode parser locations become editor UTF-16 offsets. Exact submission snapshots prevent navigation into edited SQL or a different statement. No reference implementation was copied.

Routine workflow review: [Beekeeper's public functions/procedures announcement](https://www.beekeeperstudio.io/blog/release-1.9) describes sidebar discovery, signatures and return types. No implementation or commercial source was read. Klyndb independently uses [PostgreSQL pg_proc](https://www.postgresql.org/docs/16/catalog-pg-proc.html) and [native definition/identity functions](https://www.postgresql.org/docs/16/functions-info.html), with fixed catalog pages and lazy definitions rather than eager source loading.

MySQL/MariaDB and SQL Server routine catalogs independently use native INFORMATION_SCHEMA / sys catalog metadata and native definition reads, as linked in [ROUTINES.md](ROUTINES.md). The existing capability-gated browser is reused; no additional reference implementation or commercial source was read.

PostgreSQL structural definitions independently use native PostgreSQL catalogs and decompilation functions, linked in [the PostgreSQL guide](POSTGRES.md). Materialized-view discovery reuses the existing table-opening and Structure workflow. No additional reference implementation or commercial source is read or reused.

## Query library reference — 2026-10-03

Reviewed only Beekeeper Studio's public [saved-query workflow](https://docs.beekeeperstudio.io/user_guide/sql_editor/saving_queries/) and [editor/history workflow](https://docs.beekeeperstudio.io/user_guide/sql_editor/editor/). The reference names saved SQL and retains connection-scoped execution history. Klyndb independently reuses its existing local saved-query document and 500-entry history, adding literal search, explicit original-connection filters, favorite/failed-run filters and named history-to-saved copies. No implementation source or commercial directory was read or reused. Preview 2's earlier library remains separate from these newer source controls.

CTE/derived-table completion is independently implemented through the installed CodeMirror SQL syntax tree. Public [CodeMirror SQL APIs](https://codemirror.net/docs/ref/#lang-sql) and [Beekeeper SQL editor documentation](https://docs.beekeeperstudio.io/user_guide/sql_editor/editor/) inform the alias/period-triggered workflow and identifier quoting; no Beekeeper implementation or commercial source is used. Native metadata is requested only for wildcard expansion, never by executing SQL. Scope, supported projections and remaining semantics are documented in [SQL_COMPLETION.md](SQL_COMPLETION.md).
